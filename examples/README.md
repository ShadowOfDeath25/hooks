# Example integration

A small, runnable end-to-end demo of Hooks:

```
publisher.js  ──POST /events──▶  Hooks API  ──▶  Redis queue  ──▶  worker
                                                                     │
                                            signed HTTP request      │
                                                                     ▼
                                                          mock-receiver.js
                                                     (verifies the signature)
```

| File                   | What it does                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| `publisher.js`         | Publishes an event to `POST /events` on a timer. No manual requests needed.                        |
| `mock-receiver.js`     | Receiving application. Verifies the HMAC signature, replay window and `Event-Id`, then replies.     |
| `secrets.example.json` | Template for the signing secrets the receiver loads.                                               |
| `secrets.json`         | Generated by `npm run db:seed`. Git-ignored.                                                       |

## Run it with Docker (recommended)

From the repository root:

```bash
cp .env.example .env        # only the first time; fill in the values
docker compose up --build   # starts app, worker, redis, db, mock-server, publisher
docker compose exec app npm run db:push
docker compose exec app npm run db:seed
```

`db:seed` creates the `Mock server` consumer with six endpoints pointing at
`http://mock-server:4000/...` and writes their signing secrets to
`examples/secrets.json`. Restart the receiver so it picks the new file up:

```bash
docker compose restart mock-server publisher
```

Then watch the demo run by itself:

```bash
docker compose logs -f publisher mock-server worker
```

Every `EXAMPLE_PUBLISH_INTERVAL_MS` milliseconds you should see:

- `publisher` — `Published event #1 -> event_id 12` followed by a delivery summary
- `worker` — one delivery job per active endpoint
- `mock-server` — an incoming `POST /success` with a valid signature

## Run it without Docker

Start Postgres and Redis yourself, point `.env` at them, then in three terminals:

```bash
npm run dev                 # API on :3000
npm run worker:dev          # delivery worker
npm run example:receiver    # receiver on :4000
npm run example:publisher   # automated publisher
```

Outside Docker the seeded endpoint URLs (`http://mock-server:4000`) are not
resolvable, so either run the receiver at that hostname or update the endpoint
URLs to `http://localhost:4000` with `PATCH /consumers/:consumerId/endpoints/:id`.

## Configuration

The publisher reads these from the environment (all optional):

| Variable                      | Default              | Meaning                                              |
| ----------------------------- | -------------------- | ---------------------------------------------------- |
| `HOOKS_API_URL`               | `http://localhost:3000` | Base URL of the Hooks API.                         |
| `HOOKS_API_KEY`               | `dev-secret-1`       | Sent as `x-api-key`. Seeded by `npm run db:seed`.     |
| `EXAMPLE_CONSUMER_NAME`       | `Mock server`        | Consumer to publish for. Created if it is missing.    |
| `EXAMPLE_EVENT_TYPE`          | `example.ping`       | `eventData.type` of each published event.             |
| `EXAMPLE_PUBLISH_INTERVAL_MS` | `5000`               | Delay between publishes.                              |
| `EXAMPLE_EVENT_COUNT`         | `0`                  | How many events to publish. `0` means run forever.    |
| `EXAMPLE_SUMMARY_DELAY_MS`    | `1500`               | Wait before reading `GET /events/:id` back.           |
| `EXAMPLE_STARTUP_TIMEOUT_MS`  | `60000`              | How long to wait for the API on startup.              |

The receiver reads `MOCK_PORT`, `MOCK_TIMEOUT_MS` and `MOCK_SECRETS_PATH`.

## Receiver routes

| Route              | Behaviour                                                       |
| ------------------ | --------------------------------------------------------------- |
| `POST /success`    | Always `200`.                                                     |
| `POST /status/:code` | Replies with the status code in the path.                       |
| `POST /timeout`    | Waits `MOCK_TIMEOUT_MS` before replying, to trigger client timeouts. |
| `POST /fail-twice` | Fails the first two attempts of an event, succeeds afterwards.    |
| `GET /_mock/log`   | Last 100 received requests.                                       |
| `GET /_mock/state` | Attempt counters and processed event IDs.                         |
| `POST /_mock/reset`| Clears the log and counters.                                      |
| `GET /health`      | Liveness check.                                                   |

Every webhook route rejects a request unless it carries an `Event-Id`, a
`Webhook-Timestamp` inside a five minute window, and a `Webhook-Signature`
of the form `v1,<base64 HMAC-SHA256 of "eventId.timestamp.rawBody">`.
Repeated deliveries of an already-processed `Event-Id` are answered with
`duplicate ignored`, which is how a real consumer stays idempotent.

## Notes

- The seeded consumer has six endpoints, so one published event fans out to six
  deliveries: success, retry and timeout paths are all exercised at once.
- Endpoints whose last `WEBHOOK_MAX_FAILURES` (default 5) deliveries all failed
  are auto-disabled, so the `/status/400`, `/status/500` and `/timeout`
  endpoints go quiet after a few minutes. Re-run `npm run db:seed` to reset.
